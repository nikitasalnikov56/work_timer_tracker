# Учёт рабочего времени

Небольшое Flutter-приложение (web и desktop) для учёта рабочего времени сотрудников:
добавление сотрудников, таймер с описанием задачи, отчёт за период.
Данные сохраняются локально и переживают перезапуск. Все данные в примерах вымышлены.

## Возможности

- **Сотрудники.** Добавление по имени. Пустые имена и дубликаты (без учёта регистра) отклоняются.
- **Таймер.** «Старт» с описанием задачи и «Стоп». Время идёт в реальном времени.
  У сотрудника может быть только один запущенный таймер. Повторный запуск, в том числе двойной клик, отклоняется с понятным сообщением.
  У разных сотрудников таймеры независимы.
- **Отчёт.** Записи и итог по каждому сотруднику за период: «Сегодня», «7 дней», «Этот месяц» или произвольный диапазон.
  Есть фильтр по сотруднику и общий итог. Если за период записей нет, показывается отдельное пустое состояние.
- **Сохранение.** Данные хранятся в SharedPreferences (в браузере — localStorage).
  Запущенный таймер после перезапуска приложения продолжает идти.

## Запуск

Нужен Flutter 3.24+ (stable).

```bash
# 1. Один раз: сгенерировать платформенные папки (web/, windows/ …).
#    Существующие файлы проекта команда не трогает.
flutter create . --platforms=web,windows,macos,linux --project-name work_time_tracker

# 2. Зависимости
flutter pub get

# 3. Запуск
flutter run -d web-server --web-port 8080   # затем откройте http://localhost:8080 в обычном браузере
flutter run -d windows                      # или macos / linux

# Проверки
flutter analyze
flutter test
```

### Почему не `flutter run -d chrome`

В вебе данные лежат в `localStorage`, а он привязан к профилю браузера и к origin
(схема + хост + **порт**). `flutter run -d chrome` при каждом запуске открывает Chrome
с **новым временным профилем** на **случайном порту**, поэтому после полного перезапуска
`localStorage` пустой. Внутри одного запуска (hot restart `R`, перезагрузка вкладки) данные сохраняются.

Чтобы данные переживали перезапуск:

- **Разработка:** `flutter run -d web-server --web-port 8080` и обычный браузер.
  Профиль ваш, порт фиксированный, origin не меняется.
- **Как у пользователя:** собрать и раздать статикой с фиксированным портом:
  ```bash
  flutter build web --release
  cd build/web && python -m http.server 8080
  ```
- **Демо на GitHub Pages:** origin постоянный, данные сохраняются между визитами.

Данные также пропадут, если открыть приложение в режиме инкогнито или очистить данные сайта.

## Архитектура

Слоистая архитектура: зависимости направлены внутрь, домен ничего не знает о Flutter и способе хранения.

```
lib/
├── main.dart                  точка входа: создаёт хранилище и запускает приложение
├── app/                       сборка приложения
│   ├── dependencies.dart      composition root — единственное место выбора реализаций
│   ├── app.dart               MaterialApp, провайдеры, локализация
│   └── home_page.dart         вкладки «Трекер» / «Отчёт»
├── core/                      общие абстракции без бизнес-смысла
│   ├── clock.dart             источник «сейчас» (подменяется в тестах)
│   ├── id_generator.dart
│   ├── serial_executor.dart   очередь операций (защита от гонок)
│   └── storage/               контракт KeyValueStore и StorageException
├── domain/                    чистый Dart: сущности, правила, сценарии
│   ├── entities/              Employee, TimeEntry, DateRange, TimeReport
│   ├── repositories/          интерфейсы репозиториев
│   ├── services/              TimeTrackingService, ReportService
│   └── errors.dart            доменные ошибки с текстом для пользователя
├── data/                      реализация хранения
│   ├── local/                 SharedPreferences / in-memory, JSON-маппинг
│   └── repositories/          локальные репозитории с кэшем в памяти
└── presentation/              UI на flutter_bloc (Cubit)
    ├── tracker/               список сотрудников, таймеры, диалог добавления
    ├── report/                фильтры и отчёт
    └── common/                форматирование, тикающий таймер, заглушки
```

Ключевые решения:

| Решение | Почему |
|---|---|
| Бизнес-правила в `domain/services`, а не в виджетах | Их можно проверить unit-тестами без UI, а UI только отображает состояние |
| `Cubit` из flutter_bloc | Для двух экранов с простыми событиями этого достаточно; полноценный Bloc был бы лишним |
| `KeyValueStore` + JSON | Хранилище меняется одной строкой в `dependencies.dart`; в тестах используется in-memory |
| Абстракция `Clock` | Тесты проверяют «прошло 90 минут» без реального ожидания |
| Время хранится в UTC | Смена часового пояса устройства не сдвигает сохранённые записи |
| Версия в ключе хранилища (`employees_v1`) | Задел для миграции формата данных |
| Повреждённые данные → `StorageException` | Иначе при первой же записи битые данные молча заменились бы пустыми |

### Как считается отчёт

- Запись учитывается только той частью, что попала в период. Работа с 23:00 до 01:30 даёт 1:00 в первый день и 1:30 во второй.
- Запущенный таймер считается до текущего момента.
- Период — полуинтервал `[первый день 00:00; следующий за последним днём 00:00)`.
  Конец считается как `DateTime(y, m, d + 1)`, а не `+ Duration(days: 1)`, потому что в дни перехода на летнее время сутки длятся не 24 часа.
- Запись, закончившаяся ровно в полночь, в следующий день не попадает.

### Найденные ошибки и как они исправлены

**Найдено при ручной проверке**

- **Данные в веб-версии пропадали после перезапуска.**
  Добавил сотрудников, на следующий день перезапустил `flutter run -d chrome` — список пуст.
  *Причина:* не в коде. `localStorage` привязан к профилю браузера и origin (включая порт),
  а `flutter run -d chrome` каждый раз запускает Chrome с новым временным профилем на случайном порту.
  Проверка: после hot restart (`R`) и перезагрузки вкладки данные на месте — сохранение работает.
  *Исправление:* команда запуска в README заменена на `flutter run -d web-server --web-port 8080`
  с обычным браузером, добавлен раздел «Почему не `flutter run -d chrome`».

**Исправлено в коде после ревью сгенерированного варианта**

1. **Неоднозначные finder'ы в widget-тесте.**
   Первая версия `HomePage` держала обе вкладки в `IndexedStack`. Виджеты неактивной вкладки оставались в дереве и находились finder'ами.
   Например, `DropdownButton` в отчёте строит скрытые пункты с именами сотрудников, и `find.text('Анна Смирнова')` нашёл бы два виджета.
   *Исправление:* неактивная вкладка не строится; её состояние и так хранится в Cubit.
2. **`context.read` внутри `build`.**
   В `ElapsedTimeText` и фильтрах отчёта провайдеры читались прямо в `build`. Это нарушает рекомендации provider/bloc.
   *Исправление:* `context.watch` для часов, `context.read` — только в обработчиках нажатий.

**Риски, выявленные при ревью и закрытые до первой сборки**

3. **Двойной клик по «Старт» → два таймера.**
   Проверка «нет ли активного таймера» и сохранение записи — разные асинхронные шаги, так что два быстрых вызова оба видели бы «таймера нет».
   *Решение:* изменяющие операции сервиса идут через очередь `SerialExecutor`, а кнопки блокируются на время операции (`busyEmployeeIds`).
   *Тест:* «два одновременных запуска (двойной клик) дают одну запись».
4. **Запись через полночь.**
   Если фильтровать записи по `startedAt`, работа 23:00–01:30 целиком ушла бы во вчерашний день.
   *Решение:* учитывается пересечение записи с периодом (`DateRange.overlap`).
   *Тест:* «запись через полночь делится между днями».
5. **Переход на летнее/зимнее время.**
   Конец периода, вычисленный как `+ Duration(days: 1)`, в такие дни съезжает на час.
   *Решение:* следующий день считается как `DateTime(y, m, d + 1)`.
6. **Граница ровно в 00:00.**
   Запись, закончившаяся в полночь, попала бы в следующий день с длительностью 0.
   *Решение:* условие в `DateRange.intersects`.
   *Тест:* «запись, закончившаяся ровно в полночь, не попадает в следующий день».
7. **Перевод системных часов назад.**
   Длительность могла стать отрицательной.
   *Решение:* `TimeEntry.stoppedAt` и `durationAt` не дают конца раньше начала.
   *Тест:* «перевод часов назад не даёт отрицательной длительности».
8. **Повреждённые данные.**
   Если битый JSON считать пустым списком, первая же запись затёрла бы данные окончательно.
   *Решение:* выбрасывается `StorageException`, UI показывает ошибку с кнопкой «Повторить».
   *Тест:* «повреждённые данные не затираются молча».
9. **Гонка фильтров отчёта.**
   При быстрой смене периода ответ на старый запрос мог прийти позже нового и перезаписать его.
   *Решение:* `ReportCubit.load` сверяет параметры запроса с текущими перед `emit`.
10. **Зависание widget-теста.**
    Пока идёт таймер, `Timer.periodic` планирует кадры бесконечно, и `pumpAndSettle` упал бы по таймауту.
    *Решение:* после старта тест использует `pump`, а время двигается через подменяемые часы `FakeClock`.
